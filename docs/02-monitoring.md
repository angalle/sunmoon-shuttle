# 02 — 장애 모니터링 계획 (선문대 셔틀버스 시간표 앱)

작성: ProjectCreator(총괄) · 2026-10-05

> 이 앱은 **서버가 없다**(정적 + Actions). 모니터링 대상은 "서버 가용성"이 아니라 **① 수집 파이프라인 건강 ② 데이터 신선도 ③ 앱이 읽는 계약 데이터 무결성** 세 가지다.
>
> ⚠️ **수집 방식 정정(2026-10-05 실측)**: `robots.txt` 가 `Disallow: /Page`(=**`/Page2/…` 포함**)로 시간표 URL 을 차단한다 → **자동 cron 수집을 하지 않는다**. 정본은 **사람이 브라우저로 저장한 HTML 스냅샷을 `data/raw/` 에 커밋 → 파서가 자동 정규화 → 배포**하는 경로다(`docs/01 §8`).
> 따라서 M1(수집 성공률)은 "**스냅샷 반영 성공률**(파서·검증 통과)" 로, M2(데이터 나이)는 "**원본 `sourceUpdatedAt` 과 우리 반영 시각의 차이**" 로 해석한다. 학기 개편 시 반영이 늦으면 M2 경고가 뜨는 것이 정상 동작이다.

## 2. 알림 경로
| 심각도 | 경로 | 내용 형식 |
|---|---|---|
| 심각 | **GitHub Actions 실패 알림(이메일)** + 총괄이 프로젝트 채팅에 보고 | 실패 스텝·오류 원문·마지막 정상 `fetchedAt` |
| 경고 | Actions **경고 스텝**(실패 아님) + 주 1회 다이제스트(커밋 주석) | 지표 표 + 추세 |

- **알림이 조용해도 이상하다고 판단하는 조건**: M4(7일 무변경 + 학기 시작 근처) · M2(48h 초과). 서버가 없으므로 "무소식 = 정상"이 아니다 — **신선도로 판단**한다.

## 3. 장애 시나리오별 복구 절차 (runbook)
### R1. 파서 실패(원본 HTML 구조 변경)
1. Actions 로그에서 **실패 위치**(어느 표·어느 열) 확인
2. 원본 HTML 을 `data/raw/` 에 수동 저장(스냅샷) → 파서 수정 → **골든 재생성**
3. `npm run test` 0 fail 확인 후 push → Actions 재실행
4. **사용자 영향**: 앱은 마지막 정상 데이터로 계속 동작(F8). 앱의 신선도 표시가 오래된 날짜를 보여준다(정직한 상태)

### R2. 사이트 차단(403/429) 또는 접속 불가
1. 요청 간격·UA·시간대 재확인(저빈도 원칙)
2. 2회 연속 실패 시 **수집 일시 중단**(차단 악화 방지) + 사용자에게 상태 표시
3. 필요 시 **수동 스냅샷 커밋 경로**(사람이 브라우저로 저장한 HTML 을 `data/raw/` 에 넣고 `npm run scrape -- --local`)

### R3. 데이터 손상(부분 표·빈 배열)
1. 스키마 검증(M3)이 차단하므로 **커밋되지 않는다** — 그래도 들어간 경우 `git revert` 로 직전 정상 커밋 복원
2. 원인 분석: 파서 규칙 추가 → 골든 테스트 보강(같은 손상이 재발하지 않게)

### R4. 학기 개편(노선 추가/폐지)
1. 원본에서 노선·요일 목록 재수집 → `routes[]` 변화 확인
2. 스키마 검증의 **필수 조건 갱신**(예: 노선 수 ≥ N) → 골든 재생성 → 배포
3. 앱 표시: 새 노선이 자동 노출(앱 재배포 불필요 — 데이터만 갱신)

### R5. 배포 실패(GitHub Pages)
1. Actions `deploy` 로그 확인 → 직전 배포는 **그대로 서비스**(정적 호스팅 이점)
2. 캐시 무효화 필요 시 `sw.js` 버전 올려 재배포(사용자 캐시 갱신)

| 대상 | 보존 | 위치 |
|---|---|---|
| Actions 실행 로그 | 90일(무료 기본) | GitHub Actions |

## 5. 배포 전 스모크(정기)
배포 워크플로가 매번 실행: ① 골든 파서 테스트 ② 도메인 규칙 테스트 ③ `data/timetable.json` 스키마 검증 ④ 정적 빌드 ⑤ 헤드리스 브라우저 스모크(첫 화면 렌더·오프라인 재현·콘솔 오류 0) ⑥ 결과를 `.session-notes/` 에 기록.
